# NightBridge 26.5 Release Notes Draft

NightBridge 26.5 is the first CalVer hardening milestone for a headless-first
LocalSend-compatible file-transfer stack. It targets homelab, NAS, server, and
desktop-adjacent workflows where a daemon, CLI, API, and operator documentation
matter as much as a GUI.

This is a release notes draft until the final 26.5 preflight, demo evidence,
and release retro are complete.

## What 26.5 Includes

- Headless daemon with LocalSend v2 compatibility and native transfer support.
- CLI for status, inbox, LocalSend-compatible sends, native sends, WAN lookup,
  and send-by-peer operations.
- HTTP/gRPC daemon API protected by bearer tokens.
- WebUI and TUI status/operations surfaces.
- Native QUIC + TLS 1.3 transfer path with Ed25519 identity material and trusted
  peer certificate fingerprint verification.
- Self-hosted WAN rendezvous control plane for native direct-path discovery.
- Tauri desktop GUI scaffold with remote daemon mode and standalone local daemon
  mode.
- Hook delivery, metrics, health/readiness endpoints, packaging skeletons, and
  release artifact scripts.
- Operator, user, deployment, security, interop, and release documentation.

## LocalSend Compatibility

LocalSend v2 compatibility remains a first-class boundary. The daemon can
receive from official LocalSend peers and the CLI/daemon can send to compatible
LAN peers through the LocalSend v2 path.

The LocalSend compatibility path intentionally preserves official-app
self-signed TLS behavior where required. That exception is isolated from the
native protocol and must not be reused by native sends.

Current interop status is tracked in the
[LocalSend interop matrix](../interop/localsend-matrix.md).

## Native Protocol

The native protocol uses QUIC and TLS 1.3 with Ed25519 peer identity material.
Sprint 7 hardens the native trust boundary by binding native sends to trusted
peer certificate fingerprints.

Native production paths now reject:

- unknown peers
- blocked peers
- missing native certificate metadata
- mismatched native certificate fingerprints

Direct native URL sends require explicit certificate fingerprint material when
trusted peer metadata is not available.

## WAN Rendezvous

WAN rendezvous is self-hosted and control-plane only. It lets daemons register
and look up native QUIC candidates, then peers attempt a direct native
connection.

Rendezvous does not relay file bytes and there is no default public rendezvous
service. Operators choose their own rendezvous server, logging policy, and
retention boundary.

Known WAN limitations remain:

- symmetric NAT can block direct connectivity
- carrier-grade NAT can block direct connectivity
- strict firewalls and UDP-blocking networks can prevent native QUIC transfer
- no relay fallback is included in the open-base 26.5 path

## GUI Status

The desktop GUI is a Tauri 2 app that bundles the existing Svelte WebUI. It has
two modes:

- remote daemon mode for connecting to an existing daemon endpoint
- standalone local daemon mode for starting and managing a local daemon process

The GUI can surface WAN direct-path diagnostics from daemon transfer events.
Local macOS packaging has produced a DMG, but platform release status remains
pre-release until signing, notarization, updater, Windows, and Linux validation
are complete.

## Security Posture

The intended 26.5 security boundary is the daemon and protocol crates:

- daemon API requests require bearer-token authentication
- native sends require trusted peer policy and pinned certificate identity
- LocalSend v2 self-signed TLS compatibility is scoped to the compatibility path
- rendezvous cannot authorize transfer data or relay file bytes
- WebUI token bootstrap does not expose an unauthenticated token endpoint

Operators should read the [threat model](../security/threat-model.md),
[native trust audit](../security/native-trust-audit.md), and
[rendezvous privacy model](../security/rendezvous-privacy.md) before exposing
services outside localhost or a trusted LAN.

## Audit Status

## Known Limitations

- Final 26.5 preflight evidence has passed, but release tagging still requires
  the remaining evidence below.
- Desktop packages are unsigned until platform signing and notarization are
  configured.
- Windows and Linux desktop bundles need native host validation.
- GUI WebDriver smoke requires `tauri-driver` and an interactive-capable host.
- WAN has no relay fallback.
- Rendezvous registry state is in-memory.
- Existing trusted peers without native certificate metadata need refresh or
  re-pairing before native WAN auto-send can work.
- Docker, systemd, DEB, RPM, and generated release artifacts need validation on
  representative target hosts before broad production distribution.
